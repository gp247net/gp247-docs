# GP247 アップデートガイド

## はじめに
このドキュメントでは、GP247（S-Cart）のウェブサイトを新しいバージョンにアップデートする方法を説明します。
**稼働中のサイトにとって安全な方法**です。データもカスタマイズも失いません。
対象はサイト管理者です。技術に詳しくない方でも大丈夫です。手順どおりに進め、
コマンドを正しくコピーするだけで完了します。ポイントは **GP247 の標準コマンドを優先すること**
（`gp247:update`、`gp247:info`、`gp247:doctor`）です。パッケージ（core/front/shop）ごとの
個別コマンドをたくさん覚える必要はもうありません。

> ℹ️ **区別すべき 2 種類のコマンド:**
> - **標準コマンド（推奨）:** `gp247:update` — 1 つのコマンドで、サイトにある
>   *すべての* GP247 パッケージのアップデートを処理します。
> - **パッケージ別コマンド（上級者向け）:** `gp247:core-update`、`gp247:shop-update` など
>   — 1 つのパッケージだけを対象に実行します。通常は直接呼び出す**必要はありません**。
>   `gp247:update` が正しい順番で代わりに呼び出してくれるからです。

---

## アップデートは 2 つの作業で構成されます
GP247 のアップデートには、必ず **2 つの独立した作業**があります。**両方とも**実行してください。

1. **ソースコードの更新** — 各パッケージの新しいコードを **Composer**（`composer update`）で
   ダウンロードします。この手順で変わるのは `vendor/` フォルダ内のファイルだけです。
2. **変更をサイトに適用** — データ構造（データベース）の更新、キャッシュの再作成などを、
   標準 artisan コマンド **`gp247:update`** で行います。

> ⚠️ **注意:** `composer update` を実行するだけでは**不十分**です。手順 2 を省略すると、
> コードは新しいのにデータ構造やキャッシュが古いままになり、サイトでエラーが起きることがあります。

> ℹ️ **対応バージョン:** GP247 v2.1（最初の公開版）から。データ構造を変える変更、
> **または既存データの意味を変える変更**には、すべて自動変換の処理が付いています。
> それを `gp247:update` が実行します。手順 2 が必須なのはこのためです。また、`php artisan migrate`
> を自分で実行する必要が**一切ない**のもこのためです。どの変換処理も再実行しても安全です。
> コマンドを 2 回実行しても、それ以上は何も変わりません。

## アップデート前の準備

1. **最初にバックアップを取ります。** **データベース**とソースコードのフォルダをバックアップします。
   これが最も大切な手順です。問題が起きても、いつでも元のバージョンに戻せます。

2. **現在のバージョンを確認します。** **ターミナル**（Windows では「コマンド
   プロンプト」）を開き、ウェブサイトのルートフォルダに移動して、次のように入力します。

   ```bash
   php artisan gp247:info
   ```

   成功すると、インストール済みパッケージ（core / front / shop）のバージョンが一覧表示されます。
   アップデート後に比較できるよう、この数字を控えておいてください。

3. **（推奨）環境を確認します。** 診断コマンドを実行して、サーバーが条件を満たしているか
   確認します（PHP のバージョン、必須拡張モジュール、ファイルの書き込み権限、DB 接続）。

   ```bash
   php artisan gp247:doctor
   ```

   すべての項目が **OK** なら、安心してアップデートできます。**fail** の項目があれば、
   先にその項目を完全に解決してからアップデートしてください。

## アップデート手順（標準・推奨の方法）

1. ターミナルでウェブサイトのルートフォルダに移動します。

2. Composer で**新しいソースコードをダウンロード**します。使っているパッケージに合わせて実行します。
   わからない場合は 3 つとも実行してかまいません。存在しないパッケージはスキップされます。

   ```bash
   composer update gp247/core
   composer update gp247/front
   composer update gp247/shop
   ```

   成功すると、Composer がアップグレードされたパッケージの一覧を表示します。

3. 標準コマンド 1 つで**変更をサイトに適用**します。

   ```bash
   php artisan gp247:update
   ```

   このコマンドは、次の処理を自動で順番に行います（安全で、データを壊しません）。
   - **core** を更新します。
   - **shop** のデータ構造をアップグレードします（shop モジュールがインストールされている*場合のみ*）。
   - 使用中のデータより新しいファイルを持つ**プラグイン／テンプレートのデータ更新**を適用します（たとえば
     プラグインを `git pull` した直後など）。詳しくは下の C 項を参照してください。
   - サイトが新しいコードを読み込めるよう、**キャッシュ**（route/config）を再作成します。

   成功すると、実行した手順が表示されます（例: `gp247:core-update`、
   `gp247:cache-rebuild`）。

4. **最後に確認します。** もう一度 `php artisan gp247:info` を実行し、準備のときに控えた
   バージョン番号と比べます。新しいバージョンになっていれば完了です。サイト（トップページと
   管理画面）を開いて、正常に表示されることも確認してください。

> ✅ ほとんどのウェブサイトでは、**上の 4 つの手順で十分**です。以下の項目は、特別な必要が
> あるとき（翻訳の再取得、公開済みの画面デザインの再作成など）にだけ使います。

## 上級者向けオプション

### A. 言語ファイルの再取得（`--overwrite-lang`）
既定では、`gp247:update` は管理画面で自分で修正した翻訳を**そのまま残します**。
パッケージの最新の既定翻訳を取り込みたい場合（これまで修正した言語文字列は**上書きされます**）は、
次のオプションを追加します。

```bash
php artisan gp247:update --overwrite-lang
```

> ⚠️ **注意:** 翻訳を既定値に本当にリセットしたいときだけ使ってください。多く修正している場合は、
> 先に言語テーブルをバックアップしてください。詳しくは
> [言語システム](./language-system_ja.md)のドキュメントを参照してください。

### B. 公開済みの画面デザイン／アセットの再作成（`--publish=<tokens>`）
`composer update` が更新するのは `vendor/` 内のコードだけです。外部に**公開（publish）**済みの
画面ファイル（`public/GP247` 内の管理画面 CSS/JS、`resources/views/vendor/…` 内の view、
`app/GP247/…` 内のストアフロントのテンプレート）は、自動では上書き**されません**。これらを
更新したい場合は、`--publish` オプションに「トークン」の一覧（カンマ区切り）を指定します。

```bash
php artisan gp247:update --publish=core-public                 # 安全: ビルド済みの管理画面 CSS/JS だけを更新
php artisan gp247:update --publish=core-public,front-view      # ストアフロントのテンプレートも上書き（データを破壊）
php artisan gp247:update --publish=all                         # すべてを更新（データを破壊 — 先にバックアップ）
```

有効なトークン: `core-public`、`core-view`、`front-public`、`front-view`、
`shop-view-admin`、`shop-view-front`、`all`。

> 📖 各トークンがどのフォルダに影響するかは、
> [コマンドラインリファレンス](./command-line-reference_ja.md)の「`gp247:update`」の項を参照してください。

### C. `git pull`、Composer、手動コピーでプラグイン／テンプレートを更新した場合

> ℹ️ **対応バージョン:** 2026-09-29 の更新から

拡張機能ライブラリで「更新」(Update) を押すと、GP247 はファイルを置き換えるとともに、新しいバージョンに
必要な**データ更新**（新しい設定の追加、古いデータの変換など）も実行します。プラグイン／テンプレートの
ファイルを別の方法（`git pull`、Composer、FTP、フォルダのコピー）で置き換えた場合は、**ファイル**だけが
変わり、データの部分は**まだ**実行されていません。

GP247 は拡張機能ごとにインストール済みのバージョンを記録しています。そのため、このケースを検出でき、
足りない部分を適用する方法を 3 つ用意しています（どれか 1 つを選びます）。

1. いつもどおり `php artisan gp247:update` を実行します。このコマンドには、すべてのプラグインとテンプレートに適用する手順が含まれています。
2. 拡張機能の部分だけを実行します。

   ```bash
   php artisan gp247:ext-update --local --all --type=plugin --dry-run   # プレビューのみ（まだ何もしない）
   php artisan gp247:ext-update --local --all --type=plugin             # すべてのプラグインに適用
   php artisan gp247:ext-update --local --type=plugin --key=InOut       # または 1 つのプラグインだけ
   ```

3. コマンドラインが使えない場合（共有ホスティング）: 管理画面の「プラグイン」（または「テンプレート管理」）を開きます。
   適用待ちの拡張機能には、「バージョン」列に黄色のラベル **「データ更新待ち: x → y」** が表示されます。
   「操作」列の **「データ更新を適用」** ボタン（データベースのアイコン）を押します。

注意点:
- 何度実行しても安全です。適用済みの拡張機能はスキップされます。
- 2026-09-29 より前にインストールしたサイトには、バージョンの記録がありません。そのため**初回**は、
  インストール済みのプラグイン／テンプレートがすべて「待ち」と表示されます。一度適用すれば解消します。
- ある拡張機能のデータ更新がエラーになっても、新しいファイルはそのまま残ります（ライブラリからの
  更新のように自動では元に戻りません）。原因を直してから再実行してください。完了するまで、`gp247:doctor`
  は `extension_data_pending` の項目を報告します。

## 条件と制約（操作の前に確認）

**通常のアップデート（`gp247:update`）を実行するとき**

- **稼働中のサイトでも安全** — このコマンドは*アップグレード*だけを行い、データを壊す
  再インストール（re-install）の手順は一切実行しません。そのため本番サイトでもそのまま使えます。
- **制限のあるホスティングでも実行可能** — cron、キューワーカー、websocket は必要ありません。
  `php artisan` コマンドを実行できれば、サイトを完全にアップデートできます。
- **shop の手順は shop がインストール済みの場合のみ** — shop モジュールがインストールされていない
  サイトでは、shop のアップグレードを自動でスキップし、エラーも出しません。

**`--overwrite-lang` を使うとき**

- **自分で修正した翻訳がパッケージの既定値で上書きされます** — このため、このオプションは既定で
  有効になっていません。意図的にリセットしたいときだけ有効にしてください。

**`--publish=<tokens>` を使うとき**

- **安全なのは `core-public` だけです** — これはビルド済みの管理画面 CSS/JS で、上書きしても
  カスタマイズは失われません。
- **それ以外のトークンはすべてデータを破壊します** — view／テンプレートを上書きするため、
  その場で修正した**画面デザインのカスタマイズが消えます**。先に対象フォルダをバックアップしてください。
- **`--force` フラグはありません** — データを破壊するトークンを*自分で入力した*こと自体が同意と
  みなされます。対話型のターミナルで実行した場合は、誤操作を防ぐため、コマンドが**警告して確認を
  求めます**（既定は「いいえ」）。
- **トークンを打ち間違えると、何もせずにすぐ停止します** — 無効なトークンを入力した場合、
  コマンドはアップデートを始める*前に*エラーを表示して終了します。サイトには一切影響しません。

## よくある質問（Q&A）

**Q1: `composer update` だけ実行すればよいですか？`gp247:update` は必要ですか？**

→ 両方の実行が必須です。`composer update` は新しいコードを `vendor/` にダウンロードするだけです。
変更（DB の更新、キャッシュの再作成）を実際にサイトに適用するのは `gp247:update` です。

**Q2: `gp247:core-update`、`gp247:shop-update` などをパッケージごとに覚える必要がありますか？**

→ いいえ。標準コマンド `gp247:update` を使ってください。パッケージ別のコマンドを正しい順番で
自動的に呼び出し、shop の部分はサイトに shop がインストールされている場合だけ実行します。

**Q3: `gp247:update` を実行すると、データやカスタマイズは失われますか？**

→ いいえ。既定では安全なアップグレードだけを行います。データはそのまま、自分で修正した翻訳も
そのまま、公開済みの view／テンプレートにも触れません。上書きが起きるのは、`--overwrite-lang`
または `--publish`（`core-public` 以外のトークン）を*自分で*追加したときだけです。

**Q4: cron やキューのない共有ホスティングでもアップデートできますか？**

→ できます。`gp247:update` には cron、キューワーカー、websocket は必要ありません。
`php artisan` を実行できれば十分です。

**Q5: アップデート後、管理画面の CSS/JS がおかしくなったらどうすればよいですか？**

→ ビルド済みの管理画面アセットを更新します（安全で、カスタマイズは失われません）。
`php artisan gp247:update --publish=core-public`。

**Q6: `--publish=all` と `--publish=core-public` の違いは何ですか？**

→ `core-public` は管理画面の CSS/JS だけを更新します（安全）。`all` は view／テンプレートを含めて
**すべて**を更新するため、**画面デザインのカスタマイズが上書きされます**。`all` を使う前に
バックアップを取ってください。

**Q7: アップデートが成功したかどうかは、どうやって確認しますか？**

→ `php artisan gp247:info` を実行し、アップデート前のバージョン番号と比べます。新しいバージョンに
なっていて、サイトが正常に動いていれば完了です。

**Q8: アップデートの途中でエラーが出た場合、問題はありますか？**

→ `gp247:update` は手順ごとに実行し、1 つの手順でエラーが出るとそこで止まります。そのため、
サイトが中途半端な状態になることは通常ありません。エラーメッセージを読んで対処するか、
バックアップから復元してから再度試してください。

**Q9: アップデートのたびに `gp247:doctor` を実行する必要がありますか？**

→ 必須ではありません。ただし、環境の問題を早めに見つけるため、アップデート前の実行をおすすめします
（特にサーバーや PHP のバージョンを変えた直後）。アップデート後は、`extension_data_pending`
の項目で、データ更新待ちのプラグイン／テンプレートがわかります（C 項を参照）。

**Q10: GP247 のすべてのコマンドとオプションは、どこで確認できますか？**

→ [コマンドラインリファレンス](./command-line-reference_ja.md)を参照してください。GP247 の
すべての artisan コマンドを、オプションと使用例付きで一覧にしています。
